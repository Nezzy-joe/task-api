🚀 Task API

A lightweight RESTful Task Management API built with Go's standard library and SQLite.

This project started as an in-memory CRUD API and was extended in Week 3 of the FlyRank Backend Development Track by replacing the in-memory task storage with a persistent SQLite database.

The API endpoints and request/response behavior remain the same. Only the storage layer changed.

Client → Go API → SQLite (tasks.db)

The result is a CRUD API whose data survives server restarts.

🏗️ Architecture

The main change introduced in Week 3 was the storage layer.

Assignment 1

Client → API → In-memory task list

Week 3

Client → API → SQLite database

The API contract remains the same while the storage implementation changed.

The client does not need to know whether tasks are stored in memory or in SQLite.

💾 Why SQLite?

SQLite was chosen for this project because it provides persistent storage using a single database file without requiring a separate database server.

For this assignment, SQLite provides:

Simple setup — no database server is required.

Single-file storage — the database is stored in tasks.db.

Persistence — data survives when the Go server is stopped and started again.

Easy inspection — the database can be opened directly with DB Browser for SQLite.

SQLite is appropriate for this learning project because it introduces persistent database storage without unnecessary infrastructure.

📂 Database

The database file is:

tasks.db

It is created automatically when the application starts.

The application also creates the tasks table automatically if it does not already exist.

The table contains:

Column

Description

id

Primary key generated by SQLite

title

Task title

done

Completion status stored as 0 or 1

The database file is ignored by Git so that each fresh clone can create its own local database.

🌱 Seed Data

When the tasks table is empty, the application inserts three example tasks:

Learn Go
Build Task API
Connect API to SQLite

The seed operation runs only when the table is empty.

Restarting the server does not duplicate the seed tasks.

🧪 Testing the API

Get all tasks

curl -i http://localhost:8080/tasks

Get a task by ID

curl -i http://localhost:8080/tasks/1

Create a task

curl -i -X POST http://localhost:8080/tasks   -H "Content-Type: application/json"   -d '{"title":"Learn SQL"}'

Update a task

curl -i -X PUT http://localhost:8080/tasks/1   -H "Content-Type: application/json"   -d '{"title":"Learn Go deeply","completed":true}'

Delete a task

curl -i -X DELETE http://localhost:8080/tasks/1

🔒 Parameterized Queries

Database operations use parameterized SQL placeholders instead of directly inserting user input into SQL strings.

Example:

SELECT id, title, done
FROM tasks
WHERE id = ?

The task ID is supplied separately to the database driver.

This keeps database input separated from the SQL statement and helps prevent SQL injection.

🧠 Database ↔ API Consistency

SQLite is the source of truth for task data.

Changes made directly to tasks.db are reflected by the API because both the API and DB Browser read the same database file.

There is no separate synchronization layer.

🧪 Stage 4 SQL Example

One of the SQL queries executed during Stage 4 was:

SELECT * FROM tasks WHERE done = 1;

This query returns only tasks whose done value is 1, meaning they are marked as completed.
